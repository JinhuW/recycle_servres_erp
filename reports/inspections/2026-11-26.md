## Root-cause analysis

**#1, the Telegram user session.** The diagnosis is the same as in the
reports since 2026-11-23. `apps/backend/src/lib/telegramUser.ts` maps the
MTProto `RPCError` to `TelegramError('AUTH_KEY_DUPLICATED')`.
`startUserSessionLoop` (`apps/backend/src/services/fbChatTelegram.ts:861-914`)
fails to connect, logs at `:905`, and retries on the `USER_FAIL_BACKOFF_MS`
schedule, settling at 30 minutes. That is the steady ~2 lines an hour.
Telegram revokes an authorization key for good once two connections use it at
the same time. The ERP holds a Postgres advisory lock so that its own old and
new instances never overlap. That means the second connection came from
outside this prod deployment. These retries can't succeed until the session
string is replaced.

**#4, `perf_rollups`.** Railway starts the new instance and runs its
migrations while the old instance is still serving. 0256 dropped the table
under v1.481.0's timer, and that timer flushed once more before the old
instance stopped. The error can only come from a version that still has the
flush code, so it can't come back.

## Fixes deferred

- **Telegram session (#1).** The owner needs to replace the session (see the
  Summary verdict). An optional code change could also help. When
  `startUserSessionLoop` sees `AUTH_KEY_DUPLICATED`, `AUTH_KEY_UNREGISTERED`
  or `SESSION_REVOKED`, it could stop retrying, record the state, and show it
  on Leads ▸ Facebook ▸ Settings. Then the outage would appear in the UI and
  not only in the logs. Two decisions are needed first: whether the session
  should move from an env var into a sealed DB setting with a re-login flow
  (as the repo's settings rule prefers), and where the status should appear.
