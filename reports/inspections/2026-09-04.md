## Root-cause analysis

Not applicable — no error data was available to analyze. The only
code-level findings this run are descriptive, not diagnostic: areas touched
by the six releases merged to `main` since yesterday, listed for reference
if a future run regains Railway access and needs to correlate errors
against this deploy window:

- `apps/backend/src/index.ts` / `apps/backend/src/lib/log.ts` (v1.125.0,
  #260) — 4xx responses now carry their error string on the log line via
  `c.res.clone()`; 17 `console.*` call sites across 8 files in the
  money/freight paths were moved onto the structured logger. Any log-based
  triage from here forward should be noticeably richer than what earlier
  reports had access to, once Railway access exists.
- `apps/backend/src/routes/oauth/*` (DCR endpoint) and `apps/backend/src/lib/log.ts`
  (v1.125.1, #263) — a rejected `redirect_uri` during dynamic client
  registration no longer echoes caller-supplied text into the log stream;
  the refusal is now the fixed RFC 7591 code `invalid_redirect_uri`, and the
  request-logger reason field is capped at 256 characters. Worth confirming
  no `invalid redirect_uri: <...>`-shaped lines predate this fix in
  retained logs, since that was an unthrottled log-injection path (DCR is
  unauthenticated by design).
- PayPal dispute sync (v1.124.0/#251, v1.125.1/#263) — pagination now
  prefers the `next`-labeled link over any link merely carrying a
  `next_page_token` (self-links repeat one from page 2 onward on PayPal's
  API), and a stored sync error only renders as "PayPal disputes not
  authorised" on an actual 403. If dispute-sync errors show up in logs once
  access exists, check whether they predate `#263`'s fix.
- `apps/backend/migrations/0118_bank_txn_disputes.sql` — new schema in this
  window; worth checking `schema_migrations` on the production DB once
  access exists to confirm it applied.
- Migration runner connect-retry (v1.123.1/#257, refined by v1.125.1/#263)
  — now only retries connection failures a wait can fix (e.g. Postgres
  `57P03`, still starting up) and fails fast on anything else (bad
  credentials, missing database). If a future deploy's container fails to
  boot, this changes what the startup log looks like: a fast failure
  instead of ~23s of retries.
