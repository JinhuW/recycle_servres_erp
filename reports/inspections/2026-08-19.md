## Root-cause analysis

N/A — no logs were retrieved, so no error triage was possible this run.
Since production just took its first release of the streak, this run instead

**New in production today — the shipments feature (PRs #134–#140, 15 files,
~1,260 lines):**

- `apps/backend/src/shipping/index.ts:24` (`pickShippingClient`) — silently
  falls back to the stub provider whenever `SHIPSAVING_API_TOKEN` /
  `SHIPSAVING_API_URL` are unset, logging a `console.warn` rather than
  refusing to boot. This is a **deliberate** design choice per the comment at
  `index.ts:20-21` ("Unlike OCR there is no prod boot-refusal … deploys must
  not block on it"), and stub-bought rows carry `provider='stub'` so they
  can't be confused with real purchases. Consistent with the CLAUDE.md note
  on the OCR provider's silent fallback — same shape, intentionally
  repeated. **Action item, not a bug:** confirm whether `SHIPSAVING_API_TOKEN`
  is set on the `backend` Railway service. PR #140 ("warn on the shipping
  page that the feature is not ready") suggests the team already expects the
  stub to be live in prod for now — worth confirming that's the intended
  state rather than an oversight.
- `apps/backend/src/shipping/shipsaving.ts:1-8` — the file's own header
  comment flags the ShipSaving field mapping as **PROVISIONAL**, "MUST be
  verified against the sandbox before the real provider is enabled in
  production." Every parsed response throws on an unexpected shape
  (`parseRate` at `shipsaving.ts:66`, `fetchLabelPdf` at `shipsaving.ts:83`),
  and routes convert those throws to `502`. If the token is ever set without
  that sandbox verification, watch `/api/orders/*/shipments/*/rates` and
  `/buy` for `502`s with `shipsaving: unexpected … shape` in the message —
  that's this exact gap surfacing.
- `apps/backend/src/routes/shipments.ts:449-484` (buy handler) — charge →
  upload → record ordering is explicit and commented as deliberate
  (`shipments.ts:448-450`): once ShipSaving is charged, nothing after is
  allowed to turn into a client-visible error that would prompt a retry
  double-charge. A failed R2 upload is caught and swallowed
  (`shipments.ts:465-472`, logged, `upload = null`), which is correct but
  means a bought label with a missing PDF would currently be silent apart
  from that log line — another reason log access matters here specifically.
  A failure in the final `sql.begin` (`shipments.ts:475-514`) is logged with
  an explicit "PURCHASED but recording failed — reconcile manually" message
  (`shipments.ts:517-519`) and then re-thrown — this is the single
  highest-value log line to search for once access is restored, since it
  means money moved with no DB record.
- `apps/backend/src/routes/shipments.ts:537-576` (void handler) — reads the
  `fees_applied` latch under `FOR UPDATE` before clearing it and uses
  `GREATEST(other_fees - label_cost, 0)` to stay non-negative if a manual fee
  edit already lowered `other_fees` below the label cost. No issue found in
  a focused read.
- `apps/backend/src/routes/orders.ts:1503-1509` — the PO delete guard was
  correctly extended (per CLAUDE.md's "extend the existing guard" rule) to
  refuse deleting an order with a `purchased`/`in_transit`/`delivered`
  shipment, forcing a void first; the `shipments` table's `ON DELETE CASCADE`
  on `order_id` (`0092_shipments.sql`, comment lines 15-17) can then only
  ever sweep `draft`/`quoted`/`voided` rows, matching the comment's intent.
- `apps/backend/src/routes/shippingPublic.ts` — the new unauthenticated
  `/api/public/shipping/:token` route (CSRF-exempt, matching CLAUDE.md's
  documented exemption for `/api/public/*`). `loadByToken` filters to
  `status IN ('draft','quoted')` and returns a uniform 404 on any miss
  (unknown token or already-purchased), so it doesn't leak whether a token
  ever existed. No issue found.
- **No FK-index gap**: `shipments.order_id` and `shipments.created_by` both
  get explicit indexes in `0092_shipments.sql`, and `warehouses` gained no
  new FK. Consistent with the `0035`/`0040` convention in CLAUDE.md.
