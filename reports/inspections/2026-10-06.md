## Root-cause analysis

Not performed against real logs — none were reachable. One concrete, already-diagnosed production bug is visible from git state alone, and is directly relevant because it affects `db-sync`, one of the four services in this routine's scope:

- **`db-sync` nightly prod→dev copy had been silently failing every run since v1.196.1** (fixed today on `dev` as v1.211.1, RS-182, not yet on `main`/prod). Root cause: `deploy/railway-sync/sync.sh:54` runs `pg_dump` in plain SQL format with `--clean --if-exists`; such a dump opens with a line that empties `search_path` for the rest of the restore session. `deploy/railway-sync/scrub.sql` (the credential scrub that runs immediately after, inside the same restore transaction) referenced its tables unqualified — `TRUNCATE refresh_tokens, oauth_refresh_tokens, oauth_authorization_codes, oauth_pending_consent, login_attempts;` — so with `search_path` empty those names didn't resolve and the `TRUNCATE` failed with `relation "refresh_tokens" does not exist`. Because the restore runs as one transaction, each nightly failure rolled back cleanly rather than leaving dev's DB empty — so dev's data just went stale (stuck at 2026-10-02) with nothing alerting on it. Fix (commit `2e6c669`): every name in `scrub.sql` is now schema-qualified (`public.refresh_tokens`, etc.), and `tests/sync-scrub.test.ts` now runs the scrub with `search_path` emptied so a future unqualified name fails CI instead of the nightly restore. This is a good first thing to verify once Railway/db-sync log access is restored: confirm the 04:00 UTC run actually succeeds and dev's data is current again, since this bug had zero alerting for an unknown number of nights before someone (apparently) noticed dev's data was stale.
  - This fix is on `dev` only; it has not yet been merged to `main`. The `db-sync` service's behavior in production depends on which branch/image it's actually deployed from — not independently confirmable without Railway deployment data.

Everything else flagged in prior reports remains open and unverified in production, most notably from [2026-10-05](./2026-10-05.md): `vncBridge.ts`'s auth/Origin checks and the v1.209.1 hourly-reconnect fix for it (new credential-relaying surface, v1.204.0/v1.209.1), and the v1.209.0 web-submission email-reply feature's IMAP matching/DMARC-mismatch handling (new real-customer-facing outbound surface).
