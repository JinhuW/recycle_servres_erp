## Root-cause analysis

**#1–#2, the Telegram user session.** `apps/backend/src/lib/telegramUser.ts:166`
turns the MTProto `RPCError` into `TelegramError('AUTH_KEY_DUPLICATED')`.
Under v1.472.0 the error came up through `pollUpdates`
(`services/fbChatTelegram.ts:148`) into the run loop's tick
(`fbChatTelegram.ts:808`, logged at `:843`). That loop keeps the client and
retries every few seconds, which produced 445 lines in 65 minutes. After the
v1.473.0 deploy at 01:00, the session loop (`startUserSessionLoop`,
`fbChatTelegram.ts:861–912`) fails on connect and backs off to every 30
minutes (`USER_FAIL_BACKOFF_MS`, `:66`), logging at `:905`.

Telegram sends `AUTH_KEY_DUPLICATED` when one authorization key is used from
two connections at once. It then invalidates that key for good, so retrying
cannot work. Only one ERP instance is ever connected, because the session
loop holds a Postgres advisory lock (`USER_LOCK`) on the prod database. The
v1.472.0 container connected at 23:22:57 and then ran 32 minutes without
error before the key was revoked. That points to a **second client outside
prod** using the same session string at about 23:55. Candidates are a dev
ERP with the same variables (its advisory lock is in a different database,
so it would not block), a local `pnpm dev` whose `.env` holds the prod
session (`scripts/new-session.sh` copies `.env` into every worktree), or a
one-off script. The logs can't tell which one it was.

There is one minor code weakness. In user-session mode, a fatal auth error
in the run loop's tick (`:843`) is retried forever and never handed back to
`startUserSessionLoop` to release and back off. That is how v1.472.0
produced 445 lines. It only adds log noise, because the session is dead
either way, so I didn't open a PR for it (see *Fixes deferred*).

**#3, `no_slot`.** This is unchanged from the last ten nights. The claim
route answers `409 no_slot` when no fleet slot is free
(`apps/backend/src/fleet/claim.ts:387`, `:466`). The two desired workers
`worker-60-14-3` and `homelab-5` are re-ticketed about every 6 minutes, and
each exits 75 without an account (`trackers/facebook/rs_worker/entry.py:182`).
These claims cause no Facebook login.

**#4, scan 502.** OpenRouter's upstream (Azure) rejected the uploaded bytes
as not an image. The route reports an upstream failure as 502. It happened
once, the input was bad, and it is not a code path that fails on valid
input.

## Fixes deferred

- **Restore the Telegram bridge (owner).** Create a new Telegram user
  session for the bridge account and set it in the session variable on
  Railway `backend` (`production`). Before that, find and remove the second
  user of the old string: the dev ERP's variables, local `.env` files and
  worktree copies. If it stays in a local `.env`, the next `pnpm dev` will
  revoke the new key the same way. Setting a Railway variable redeploys
  `backend`. Agents may not change Railway variables, so the owner has to do
  this.
- **Optional hardening (code, low priority).** In user-session mode, treat
  `AUTH_KEY_DUPLICATED`, `AUTH_KEY_UNREGISTERED` and `SESSION_REVOKED` as
  fatal. Stop the run loop, release the lock, and log one clear
  "Telegram session revoked — re-login needed" line instead of retrying.
  Raising an ops alert would also help, since this outage was silent apart
  from logs. **Decision needed:** should a revoked session raise an ops
  alert (the `deploy/railway-alerts` relay) or show on Leads ▸ Facebook ▸
  Settings?
- **`no_slot` (owner, carried over).** Either lower the desired worker count
  on `worker-60-14` and `homelab` by one each, or free or add pool accounts.
