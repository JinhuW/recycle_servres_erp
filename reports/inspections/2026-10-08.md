## Root-cause analysis

Not performed against real logs — none were reachable. Fourteen releases landed on `main` (production) since yesterday's report, covering RS-185 through RS-203. The four new migrations are all additive/low-risk (new table, new nullable FK column, one `CHECK` relaxation) — no destructive or backfill DDL in this batch, unlike yesterday's PO-1483 data restoration:

- `apps/backend/migrations/0162_order_commission_paid_by.sql` — adds nullable `orders.commission_paid_by UUID REFERENCES users(id) ON DELETE SET NULL`. No backfill (deliberate, per the migration's own comment).
- `apps/backend/migrations/0163_sell_order_packs.sql` — new `sell_order_packs` table (Pack-mode progress, keyed on `(sell_order_id, line_key)`).
- `apps/backend/migrations/0164_sell_order_lines_qty_allow_zero.sql` — relaxes `sell_order_lines_qty_check` from `qty > 0` to `qty >= 0`, mirroring the PO-line-qty-zero change from v1.213.0 onto sell orders.
- `apps/backend/migrations/0165_sell_order_signoffs.sql` — new `sell_order_signoffs` table (per-manager sign-off, keyed on `(sell_order_id, user_id)`, with a `fingerprint` column that invalidates a sign-off when the order changes underneath it).

**Largest production-surface change today, worth the first look once access is restored:** `apps/backend/src/routes/sellOrders.ts` (+558/−… lines) and the new `apps/backend/src/routes/sellOrderPack.ts` and `apps/backend/src/services/sellOrderSignoff.ts`. Three features landed together and all touch the sell-order Done path, the point where stock is consumed and commissions start:
- **RS-198 (v1.226.0)** — Done is now refused (409) until every active manager has signed off (`sellOrderSignoff.ts`'s fingerprint check). A fingerprint mismatch bug here would either wrongly block Done (business-visible, not a crash) or wrongly allow it (silent, no error signal) — neither shows up as a log ERROR, so this needs a manual spot-check against real orders once access is back, not just an error-log scan.
- **RS-199/RS-190/RS-191/RS-193 (v1.218.0–v1.227.0)** — Pack mode's new "pack by PO line" / fold-by-product layout, backed by `sell_order_packs`. The per-line `line_qty`/`counted` CHECK constraints (`counted <= line_qty`, `line_qty > 0`) are exactly the kind of boundary condition that throws a Postgres constraint-violation 500 if the frontend and backend's idea of a line's current qty ever drift (e.g. a line edited to a lower qty after some units were already packed).
- **RS-200/RS-202/RS-203 (v1.225.0–v1.227.2)** — the PO approve/payment-mismatch flow was reworked three times in three days (RS-200 shipped, then RS-202 and RS-203 fixed regressions RS-200 and RS-202 each introduced, per `/code-review high`'s own findings recorded in the v1.227.2 changelog entry). This is the single area that has already demonstrably regressed twice this week under normal review, which makes it the top candidate for a production incident if a fourth edge case slipped through — watch `routes/orders/patch.ts` and `routes/orders/detail.ts` (both touched in this batch) for any new exception around PO approve/stage-move.
