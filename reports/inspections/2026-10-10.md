## Root-cause analysis

Not performed against real logs — none were reachable. Eleven releases landed on `main` (production) since yesterday's report, covering RS-207 through RS-226, with five new migrations (`0167`–`0171`). The two that matter most for this routine, because they can abort the *next* deploy's boot rather than just misbehave at runtime:

- **`apps/backend/migrations/0169_order_line_product_no.sql` (v1.234.0, RS-213 part 1).** Backfills a new `order_lines.product_no` from a `ROW_NUMBER()` over each PO's existing line order, then runs a `DO $$ … RAISE EXCEPTION '0169: % PO product numbers differ from the rank they replace'` guard (lines 25–34 of the migration) that aborts the migration — and, per `CLAUDE.md`'s migration-on-boot design, the container boot — if any line's backfilled number doesn't match a live recomputation of the same rank. `tests/` exercises this against the seeded template DB (green per `backend-tests`), but the guard is specifically there to catch real-world tie-breaks in `(position, created_at, id)` that a template DB with synthetic timestamps is unlikely to reproduce. This is the first thing to check once access is restored: did `backend`'s migration step succeed against the real prod `order_lines` table, or is there a `0169:` exception in the deploy logs?
- **`apps/backend/migrations/0170_sell_order_line_product_no.sql` (v1.235.0, RS-213 part 2) + `services/sellOrderNumbers.ts:442` (`freezeLegacySellNumbers`), called from `server.ts:28`.** Unlike 0169, this one isn't backfilled in SQL — the column ships `NULL`, and the backend computes and freezes every existing sell order's product `#` once, in TypeScript, **before the server starts listening** (`server.ts:24–28`: `const frozen = await freezeLegacySellNumbers(getDb(env)); if (frozen) log.info(...)`). The comment on `server.ts:27` says it plainly: "A failure stops the boot rather than serve orders that read unnumbered." Any uncaught exception in that TypeScript fold — e.g. a sell order whose lines fold ambiguously under `foldSheetLines`/`legacyNumbers` — crashes the process on every restart until the bad data is fixed or the code is patched, which is exactly a Railway crash-loop with no HTTP traffic involved at all. This is the second thing to check: `backend`'s most recent deployment logs for a `sell-order numbers frozen` info line (success) versus an unhandled exception before the `recycle-erp-backend listening` line (failure).

Both are additive, idempotent-by-design migrations with no destructive DDL — but "idempotent" and "has a hard-fail guard against production's actual data" are different properties, and only the latter is being exercised for the first time against real prod rows today, not CI's seed data.
