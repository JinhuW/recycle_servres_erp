## Root-cause analysis

Root cause of the *access gap* is confined to the inspection routine's own
environment, unchanged in kind from prior reports:

1. **No Railway API reachability.** The session's egress policy has no
   allow rule for `backboard.railway.com` — a deterministic allowlist
   denial (`CONNECT tunnel failed, response 403`), not a network flake.
2. **No Railway credential.** Even if the host were reachable, there is no
   `RAILWAY_API_TOKEN` in the environment and no Railway MCP server
   connected, so neither the GraphQL fallback nor the preferred MCP path
   could authenticate.

For the **token-leak bug fixed in v1.114.1** (source-level analysis only,
since production logs are unobservable):
- `apps/backend/src/routes/public/shipping.ts` — the route handling
  `/api/public/shipping/<token>` — the route's own doc comment states the
  token in the URL *is* the credential, but the request-logging redaction
  list (added alongside the new structured logger in v1.114.0,
  `apps/backend/src/lib/log.ts` / the request-logging middleware in
  `index.ts`) did not include this path, so the token was written to
  stdout on every seller-fill request until v1.114.1's fix.
- The client-error-report path stored `href` (full URL, including the
  token) unredacted beside an already-redacted `path` field — the CHANGELOG
  calls this "the likelier leak of the two", since a purchaser checking
  what a counterparty sees on `/v/<token>` would have that exact URL
  reported back verbatim by the client-side error reporter shipped in
  v1.105.0 (`feat(observability): record client-side failures`). The fix
  redacts the raw string rather than parsing it with `new URL()`, because
  the SPA's hash-routed relative hrefs throw on that parse.

No other application-level fault in `apps/` or `packages/` is implicated by
this routine's own findings — nothing in the application repo can grant this
routine egress or a token, and the remaining v1.105.0–v1.114.1 changes read
as ordinary feature/fix work with unit-testable scope (per their CHANGELOG
entries), not anything that stands out as a live-system risk beyond the
general "ten versions landed in one release, unverified" concern above.
