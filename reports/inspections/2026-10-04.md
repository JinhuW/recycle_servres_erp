## Root-cause analysis

Not performed — there is no log data to triage or trace back into `apps/`/`packages/` source this run.

What changed on the git side since yesterday, for context on what is now live and unmonitored:

- **v1.203.0** (RS-160, orders): POs now have a `manager_id` (`apps/backend/migrations/0156_order_manager.sql`). A manager who moves a PO with no manager into Reviewing, Ready to Pay, or Done is stamped as its manager inside that move's own transaction; a different manager moving it is asked to take over, keep the existing manager, or cancel. This is a new state-changing write path inside `routes/orders/lifecycle.ts`'s `/advance` handler — exactly the kind of change CLAUDE.md flags as lock-order– and status-guard–sensitive.
- **v1.203.1** (RS-162): fixed the desktop PO page's Save button staying enabled with nothing to save; a float/percent comparison bug (`toFixed(2)` round-trip) on the phone PO page is fixed by sharing one `rateEq` comparator between both shells.
- **v1.203.2** (RS-163, pre-release review fixes for v1.203.0–v1.203.1): eight fixes on top of the manager feature, most notably:
  - A concurrency guard: moving a PO now sends the manager the client last saw (`fromManagerId`); the server re-checks it under the row lock and refuses with a typed `OrderRefusal` (`kind: 'managerChanged'` → HTTP 409) if another manager took it over in the meantime, rather than silently overwriting.
  - Migration `0158_order_manager_backfill_past_review.sql` extends the `0156` backfill to POs that jumped straight from In Transit past Reviewing into Ready to Pay or Done, which `0156` had left with no manager.
  - A demoted/deactivated manager now reads as "no manager" rather than staying pinned to the PO forever.

I read `apps/backend/src/routes/orders/lifecycle.ts` (as it exists on `origin/main`) and the two new migrations directly from git (this branch's own checkout predates them and was not used for the read). The `managerChanged` 409 is wired through the same typed-refusal pattern (`OrderRefusal`/`refusalResponse`) as every other guard in that file, and the row is locked `FOR NO KEY UPDATE` before the manager check, consistent with the "one lock order" rule in `CLAUDE.md`. Nothing jumped out as a correctness defect on a static read; this is not a substitute for watching it under real traffic once logs are back, given it is a brand-new, frequently-hit write path (`/advance` is the common next-step action on every PO screen).

Everything from v1.202.1 and earlier was already covered in [2026-10-03's report](./2026-10-03.md) and remains unverified in production (notably: v1.201.0's Review-mode → Reviewing transition, v1.197.0's stock lock-order change, v1.195.x's public-surface rate-limiting, v1.199.0's pagination/cursor rewrite, and v1.197.1's new `CHECK` constraints).
