## Root-cause analysis

The root cause is confined to the inspection routine's environment, and is
two independent gaps that both must be closed:

1. **No Railway API reachability.** The agent proxy denies `CONNECT` to
   `backboard.railway.com:443` (HTTP 403, policy). Confirmed via the proxy
   status endpoint above — a deterministic allowlist denial, identical every
   day, not a network flake.
2. **No Railway credential.** Even if the host were reachable, there is no
   `RAILWAY_API_TOKEN` in the environment and no Railway MCP server connected,
   so neither the GraphQL fallback nor the preferred MCP path could
   authenticate.

No source-code fault in `apps/` or `packages/` is implicated — nothing in the
application repo can grant this routine egress or a token. (For reference, the
production deploy target per `CLAUDE.md` is now `origin/main`, currently
v1.70.3; the `prod` branch named in this routine's infra brief was retired
2026-07-20 and its head has not moved since, consistent with that note.)

## Recommended fixes

*(Diagnosis only — no application code or Railway config changed by this run.)*

To make this routine functional, the environment it runs in needs **both**:

1. **Allowlist `backboard.railway.com` (port 443) in the session's egress
   policy.** Until this host is permitted, every Railway API call fails with a
   403 CONNECT denial regardless of credentials. This is the primary blocker.
   Alternatively, connect a **Railway MCP server** to the session, which the

   once the host is reachable.

Both are configuration changes to the scheduled task's environment, outside the
scope of what this inspector is permitted to modify. Recommend the routine's
