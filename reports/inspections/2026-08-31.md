## Root-cause analysis

Root cause is confined to the inspection routine's own environment,
unchanged in kind from prior reports:

1. **No Railway API reachability.** The session's egress policy has no
   allow rule for `backboard.railway.com` — a deterministic allowlist
   denial (`CONNECT tunnel failed, response 403`), not a network flake.
2. **No Railway credential.** Even if the host were reachable, there is no
   `RAILWAY_API_TOKEN` in the environment and no Railway MCP server
   connected, so neither the GraphQL fallback nor the preferred MCP path
   could authenticate.

No source-code fault in `apps/` or `packages/` is implicated by this
routine's own findings — nothing in the application repo can grant this
routine egress or a token. The migration files touched by v1.103.0–v1.104.1
(`0109_warehouse_address_from_ship.sql` through
`0112_merge_duplicate_parts_per_category.sql`) are consistent with the
commit messages (warehouse ship-address backfill, part-number
normalization/merge) and ran as part of the same PRs; nothing about them is
unusual on inspection, but this routine cannot confirm they applied
cleanly against production Postgres via `_migration_ledger`, since that
also requires Railway/DB access this routine does not have.
