## Root-cause analysis

**#1, the Telegram user session.** The diagnosis is the same as in the
reports since 2026-11-23. `startUserSessionLoop`
(`apps/backend/src/services/fbChatTelegram.ts:861-914`) fails in
`connectUserClient` and logs at `:905`. It then retries on the
`USER_FAIL_BACKOFF_MS` schedule (`:66`, 60 s → 5 min → 30 min), which gives
the steady 2 lines an hour. Telegram revokes an authorization key for good
once it sees two live connections using it. The prod ERP takes a Postgres
advisory lock (`USER_LOCK`, `:62`) before it connects, so its own old and new
instances can't overlap. The second connection therefore came from outside
this deployment. The session hasn't connected since 11-22 23:22. Since then
it has failed on every deployment, including `a3095770` (v1.479.0),
`b94b0fab` (v1.481.0) and `a6759900` (v1.482.1).

## Fixes deferred

- **Telegram session (#1).** The owner needs to replace the session (see the
  Summary verdict). An optional code change, also proposed in the earlier
  reports: when `startUserSessionLoop` sees `AUTH_KEY_DUPLICATED`,
  `AUTH_KEY_UNREGISTERED` or `SESSION_REVOKED`, it stops retrying, records
  the state, and shows it on Leads ▸ Facebook ▸ Settings. Then a dead session
  appears in the UI and not only in the logs. Two decisions are needed first:
  whether the session should move from an env var into a sealed DB setting
  with a re-login flow (AGENTS.md's settings rule prefers that), and where the
  status should appear.
