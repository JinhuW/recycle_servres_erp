# Security and platform — review 2026-10-31

Lanes: A1 (Backend security/platform). 6 findings: 0 P1 / 1 P2 / 5 P3. Severity shown is after verification; P3s were not verified.

## P2

- [ ] **A1-01 / P2 / confirmed: A refresh rotation in flight during a password change or deactivation leaves the rotated session alive (cookie and OAuth)**
  - Location: `apps/backend/src/routes/me.ts:186-204; apps/backend/src/auth.ts:200-221; apps/backend/src/oauth/tokens.ts:176-221,243-251; apps/backend/src/services/members.ts:218-233`
  - Evidence: The revocations are a single READ COMMITTED `UPDATE refresh_tokens|oauth_refresh_tokens ... WHERE user_id = X AND revoked_at IS NULL` (me.ts:194-200, tokens.ts:244-247, members.ts:232-233). Both rotations lock only the token row (`FOR UPDATE OF rt`, auth.ts:213, tokens.ts:188) and then INSERT the successor. When the revoke statement blocks on the row a rotation holds, it re-checks that row after the rotation commits (now revoked, so skipped). Its snapshot predates the successor row, so it never revokes it. Neither rotation re-checks credential_version, so the successor keeps working: rotateRefresh checks only `u.active` (auth.ts:217), and rotateRefreshToken returns the live `user_cv` (tokens.ts:184,219), so the next access token carries the new cv. The self password change and deactivation take only a no-key UPDATE on users (me.ts:189-192, members.ts:222-224), which does not conflict with the FOR KEY SHARE the successor INSERT's FK check takes, so nothing serialises the two transactions. Code redemption already solves this by taking the user row FOR SHARE first (oauth/server.ts:571-583); neither refresh rotation does. Reproduced: docs/review-2026-10-31/repro/A1/refresh-vs-reset-race.test.ts, 'A1-01' block (2/2 pass twice on PG18). After a 200 from POST /api/me/password, the other family's rotated rt refreshes again (200) and GET /api/me with the new at returns 200. The OAuth family rotates again with credentialVersion equal to the post-change cv.
  - Failure: A user's laptop is stolen, or a cookie leaks. The user signs in elsewhere and changes their password, the documented way to end every other session. The stolen session's client refreshes in a loop; /api/auth/refresh has no rate limit. If one rotation is in flight when the revoke runs, its successor survives, and the thief keeps a sliding 14-day refresh family with fresh, valid access tokens indefinitely. The same holds for a connector's OAuth grant (30-day sliding). With a deactivation, the leftover row is refused while the account is inactive (auth.ts:217, tokens.ts:200) but comes back if a manager later reactivates the account. That contradicts members.ts:220-221 ('tokens minted before the deactivation stay dead').
  - Fix: Serialise rotation with credential changes on the user row. In rotateRefresh and rotateRefreshToken, lock `users` FOR SHARE (or FOR KEY SHARE) before the token row, matching the code-redemption order. Make every credential change take `SELECT ... FROM users WHERE id = X FOR UPDATE` before its revoke. Better still, stamp the family with the credential_version it was issued under and refuse rotation when it differs, so a missed row cannot outlive the change. That is the 'centralize session and credential validity' carryover.
  - Regression test: Keep the repro's two A1-01 cases with the assertions flipped: after a password change, the rotated other-family rt and OAuth refresh token must be refused, and /api/me must return 401. Add deactivate -> reactivate -> old rotated rt refused.
  - Verifier: repro/A1-verify/rotation-race.mts against disposable PG18 (port 55701, migrated to head 0220), calling the real rotateRefresh / rotateRefreshToken / deactivateMember / updateMember / revokeUserOAuthTokens and the exact revoke SQL of routes/me.ts:186-203; output in repro/A1-verify/rotation-race.out.txt. A test-only AFTER INSERT trigger (pg_sleep 1s, scoped to the rotating connection) widens the real INSERT->COMMIT window. Results: self password change during an in-flight cookie rotation -> rotation ok, 1 live row left in the 'thief' family, successor rotates again (true); control without overlap -> rotate refused. Deactivation during rotation -> successor refused while inactive (auth.ts:217 returns ok:false WITHOUT revoking), then after updateMember({active:true}) the successor rotates (true), contradicting members.ts:220-221. OAuth: self password change during rotateRefreshToken -> 1 live row, successor rotates, carries the post-change credential_version (so bearer tokens are not stale); OAuth deactivate+reactivate before next presentation -> successor rotates (true). (Mechanism verified from code and reproduced: rotateRefresh/rotateRefreshToken lock only the token row (FOR UPDATE OF rt), never users; the revoke UPDATE in me.ts / revokeUserRefreshTokens / revokeUserOAuthTokens blocks on the old row, re-checks it after the rotator commits (now revoked, skipped) and never sees the successor inserted after its READ COMMITTED snapshot. Minted access tokens after the change pass stale (iat >= tokens_valid_after, cv current) and sessionLive. Severity stays P2 rather than P1: exploitation needs an already-stolen httpOnly refresh token plus winning a millisecond-scale INSERT->COMMIT window at the moment of the revoke (a tight refresh loop makes this a probabilistic, not deterministic, bypass); the unwidened timing was not measured. The OAuth deactivation variant is partly mitigated (presenting the successor while inactive revokes the family, tokens.ts:200), the cookie variant is not. Fix direction: lock the users row (SELECT ... FOR SHARE/KEY SHARE on users in rotate, or FOR UPDATE in the revokers) so rotation and revoke serialize, or have rotate re-check credential_version/tokens_valid_after against the token's issue time.)

## P3

- [ ] **A1-02 / P3 / P3, not verified: A refresh rotation racing a manager password reset deadlocks (40P01) and one request answers 500**
  - Location: `apps/backend/src/services/members.ts:160,176-177; apps/backend/src/auth.ts:209-219; apps/backend/src/oauth/tokens.ts:182-215`
  - Evidence: updateMember takes `SELECT role FROM users ... FOR UPDATE` (members.ts:160) and then revokes refresh rows (176-177). The rotation holds the old token row (`FOR UPDATE OF rt`), and its successor INSERT needs FOR KEY SHARE on the same users row for the FK check. If the reset locks the user between the rotation's SELECT and its INSERT, each waits on the other. Reproduced in docs/review-2026-10-31/repro/A1/refresh-vs-reset-race.test.ts ('A1-02', with a BEFORE INSERT delay): one side failed with PostgresError 40P01, surfaced as HTTP 500. The OAuth variant also logged 40P01 from issueRefreshToken in the first repro run.
  - Failure: A manager resets a member's password, or demotes or deactivates them through PATCH, at the moment that member's tab refreshes. One of the two requests fails with 500 and an error-sink record. A failed refresh clears nothing, so the client retries, but a failed reset can look to the manager as if it partly applied. The window is narrow, which is why this is P3.
  - Fix: Same lock order as A1-01: rotations take the user row first, so the reset and the rotation queue rather than deadlock.
  - Regression test: Repro 'A1-02' with the assertion flipped: both requests return non-5xx.

- [ ] **A1-03 / P3 / P3, not verified: No retention for session, attempt and OAuth tables; login_attempts takes anonymous writes**
  - Location: `apps/backend/src/lib/loginAttempts.ts:51-55; apps/backend/src/auth.ts:182; apps/backend/src/oauth/tokens.ts:148; apps/backend/src/oauth/server.ts:324-328`
  - Evidence: Nothing deletes old login_attempts, refresh_tokens, oauth_refresh_tokens, oauth_authorization_codes, oauth_pending_consent or expired public_form_reservations. The only deletes are the reservation release (loginAttempts.ts:60), unconsumed codes on credential changes (tokens.ts:248-251), and the prod->dev scrub (deploy/railway-sync/scrub.sql:18-20). grep over apps/backend/src, scripts, deploy, backup and infra finds no sweeper. Every anonymous login with a well-formed email adds a row. Every hourly cookie refresh and every OAuth refresh adds a row. Every /oauth/authorize by a signed-in user parks a row that is never removed once expired.
  - Failure: The tables and their indexes grow for the life of the database. login_attempts is the one an outsider can drive. Each address gets 30 failures per 15 min, the bcrypt gate admits about 4 at a time, and random emails dodge the per-email lock, so a spread-out credential-stuffing run turns into permanent rows and index bloat on the hot login path. Nothing is broken today; it grows without bound.
  - Fix: Add a daily sweep, for example in the web-submission purge loop or a sibling: login_attempts older than about 1 day, refresh rows revoked or expired more than N days ago (keep enough for reuse detection), expired codes and pending consent, and public_form_reservations older than 10 minutes.
  - Regression test: Sweep test: seed expired and old rows plus live rows; only the expired ones go, and reuse detection still works for a family's recently revoked rows.

- [ ] **A1-04 / P3 / P3, not verified: MCP tool failures return raw error messages, including Postgres errors, and unvalidated `limit` args reach SQL**
  - Location: `apps/backend/src/mcp/server.ts:145-147; apps/backend/src/mcp/tools/market.ts:93; apps/backend/src/mcp/tools/sellOrders.ts:99,146`
  - Evidence: The tools/call catch returns `e.message` for any error (server.ts:146). index.ts:468-471 says err.message must never reach a client because postgres.js errors embed SQL detail. `limit` arrives unvalidated. `Math.min(Math.max('x', 1), 200)` is NaN, and `Math.min(-5, 100)` is -5 (sellOrders.ts:99), so LIMIT fails in Postgres. `create_sell_order_draft` casts caller ids with `::uuid[]` (sellOrders.ts:146), so a non-UUID id raises a Postgres syntax error whose text is returned verbatim.
  - Failure: Any connector token, including a purchaser's market:read grant, can send `{"limit":"x"}` or a junk inventoryId and read Postgres error text (type, column and operator detail) in the tool result. The schema exposure is small, but it is the exact class onError was hardened against, and every malformed call also lands in the error log.
  - Fix: Validate numeric and UUID args at the tool boundary with clean messages. In the catch, return e.message only for errors the tools throw on purpose (a ToolError class), and a generic 'tool call failed' otherwise.
  - Regression test: mcp-server.test: list_market_values with limit 'x' and -5, and create_sell_order_draft with inventoryId 'nope', return isError with a clean message containing no 'syntax'/'type' Postgres text.

- [ ] **A1-05 / P3 / P3, not verified: Workspace PATCH stores unvalidated values for keys the public-form budget and MCP read**
  - Location: `apps/backend/src/routes/workspace.ts:13-26,51-56; apps/backend/src/lib/settings.ts:15-19; apps/backend/src/routes/publicForms.ts:75-99`
  - Evidence: KNOWN_SETTINGS validates six keys, and any other key or value is upserted as-is. getWorkspaceSetting does no type check (it returns the stored JSON when not null). public_form_daily_submissions and public_form_daily_bytes feed `n < maxSubmissions && Number(bytes)+incoming <= maxBytes` (publicForms.ts:98). mcp.sellOrderCustomerId feeds createSellOrderDraft (mcp/tools/sellOrders.ts:166-167).
  - Failure: A manager, or a buggy settings UI, saves public_form_daily_submissions as a string such as "300 " or an object. The comparison goes false or NaN, and both public website forms return 429 'not taking more submissions today' to every seller until someone finds the setting. A bad mcp.sellOrderCustomerId makes every MCP draft fail.
  - Fix: Add validators for the budget keys (positive integers) and mcp.sellOrderCustomerId (UUID of an existing customer), or have getWorkspaceSetting fall back when the stored type differs from the fallback's.
  - Regression test: workspace PATCH with public_form_daily_submissions:'abc' returns 400; the intake form still admits after a bad legacy row is present.

- [ ] **A1-06 / P3 / P3, not verified: Shutdown stops loops without waiting for an in-flight tick; the web-submission purge loop has no stop flag**
  - Location: `apps/backend/src/lib/shutdown.ts:37-44; apps/backend/src/lib/webSubmissionPurge.ts:89-112,63-79`
  - Evidence: onShutdown calls loop.stop() and then closes the pool after server.close (shutdown.ts:37-42). stop() only clears timers. Running ticks are neither awaited nor told to stop: startWebSubmissionPurgeLoop's run() keeps batching through MAX_BATCHES_PER_RUN, and closeSharedDb ends the pool after 5 s (db.ts:66). The purge deletes R2 objects (webSubmissionPurge.ts:63) before its row DELETE (70-75).
  - Failure: A deploy lands while the daily purge is mid-batch. Its photos are deleted from R2, then the DELETE or claim release fails on the closed pool. The rows stay claimed, so a manager's PATCH or convert answers 409 'being purged' until the claim expires (1 h) and the next daily run finishes the deletion. Nothing is lost that was not already slated for deletion. It only adds noise and a stuck state.
  - Fix: Give the purge loop a `stopped` flag checked between batches. Have loops expose the promise of their current tick so onShutdown can await it (bounded by graceMs) before closeDb.
  - Regression test: shutdown.test: a loop whose tick is pending delays closeDb until it settles or graceMs passes; purge stops between batches after stop().
