# Fleet and integrations — review 2026-10-31

Lanes: A4 (Backend fleet and integrations). 6 findings: 0 P1 / 3 P2 / 3 P3. Severity shown is after verification; P3s were not verified.

## P2

- [ ] **A4-01 / P2 / confirmed: A lease that lapsed during an ERP/DB outage is claimable while its worker is still alive, so the agents' next desired poll can start new workers that steal live workers' slots (a cascade of Facebook logins)**
  - Location: `apps/backend/src/fleet/claim.ts:347-355; apps/backend/src/fleet/hosts.ts:239-265; apps/backend/src/fleet/auth.ts:254-261`
  - Evidence: Claim takes any fleet slot with lease_expires_at < NOW() (claim.ts:350), ordered first by last_host_id = the claiming host (claim.ts:352). workerCount counts a host's held slots only where lease_expires_at > NOW() (hosts.ts:242) and shares every lapsed slot out as 'free' round-robin over live hosts (hosts.ts:252-262); the 'highest' floor is computed from those held rows too (hosts.ts:263), so it is 0 after a lapse. Nothing considers fleet_workers.last_heartbeat_at or the host report's running containers. Meanwhile eligibleSlot does not check the lease at all (auth.ts:254-261), so the surviving worker would happily renew if it heartbeated first. Default lease_minutes is 30 (packages/shared/src/fleet.ts:554); a Railway outage of that length has happened before (memory: railway-outage-splits-prod).
  - Failure: Hosts A and B (capacity 10 each), A runs A-1..A-8, B runs B-1..B-4. The ERP (or its Postgres) is unreachable for >30 min, so every slot's lease lapses. On recovery B's agent polls /desired before B-1..B-4 heartbeat: held(B)=0, all 12 slots are 'free', round-robin gives B a share of 6, so desired.count rises to 6 and the agent docker-runs B-5 and B-6. B-5 claims first the slots whose last_host_id = B, i.e. B-1's lapsed slot: epoch bumps, B-1's next heartbeat gets 409 stale_epoch, B-1 exits, the agent restarts it, it claims another lapsed slot (A's), and so on. Every one of those boots is a Facebook login, against the repo's first rule.
  - Fix: Treat a lapsed slot whose worker heartbeated within the last N minutes (or whose worker_id appears as a running container in its host's latest report) as held, both in workerCount and in claim's free-slot query; or add a boot grace: for lease_minutes after the ERP process starts, claim only slots that were free (lease NULL) or whose worker is gone from every host report. Count held slots per host from the report as well as from leases so 'count' cannot jump after an outage.
  - Regression test: tests/fleet-claim.test.ts + fleet-hosts.test.ts: seed two hosts with live workers and slots, set every lease to NOW()-1min with last_heartbeat_at 2 min ago and the containers in the host reports; assert GET /hosts/B/desired keeps count at B's running workers and a claim by a new worker id on B returns 409 no_slot instead of taking B-1's slot.
  - Verifier: repro/A4-verify/a4-01-lapsed-lease.test.ts (out: repro/A4-verify/a4-01.out.txt), run against a disposable PG18 on :55704. Hosts a,b cap 10, a-1..a-8 and b-1..b-4 claimed normally; GET /api/fleet/hosts/b/desired = 4. All leases set lapsed (outage > lease_minutes 30). Then desired(b) = 6; POST /worker/claim b-5 = 200 with account 9, which was b-1's (last_host_id b ordering, claim.ts:347-355); b-1's next POST /worker/heartbeat = 409 stale_epoch. Code: workerCount (hosts.ts:239-265) counts lapsed-lease slots as free and drops them from held(); heartbeat (claim.ts:497-500) renews a lapsed lease only if it gets there first; eligibleSlot (auth.ts:254-261) checks epoch, not lease, so b-5's epoch bump fences b-1. (Reproduced end to end. Mitigations that narrow it but do not close it: workers heartbeat every 20 s (vendored monitor fleet_heartbeat_interval=20) and keep heartbeating through the outage, and the agent starts at most one worker per tick with a 3 min stagger (fleet-agent plan.ts). The window is the first agent tick after recovery (30 s poll) before every held slot has re-heartbeated, which is likely, and one steal is enough to start the 75 -> restart -> claim chain. It also gets worse when the peer host is not yet live (last_seen_at > 2 min): peers then excludes it and the polling host's share grows toward its full capacity. It needs an ERP/DB outage longer than lease_minutes, so P2 stands rather than P1.)

- [ ] **A4-02 / P2 / confirmed: Saving the pool editor overwrites a session a fleet worker resealed after the page loaded (lost update of the stored browser session)**
  - Location: `apps/backend/src/routes/facebookPool.ts:456-492 (cookie written at :484, compare at :476)`
  - Evidence: PUT /api/facebook-pool/:no writes cookie_enc from the draft unconditionally (facebookPool.ts:484). The draft is the editor's copy of the snapshot (snapshot() unseals cookie_enc for managers, :151), and the frontend draft always carries the cookie field (apps/frontend/src/lib/facebookPool.ts:39,77). The only comparison is draft.cookie === storedCookie (:476), which decides the cookie_at stamp, not whether to write; there is no version/updated_at precondition. Meanwhile PUT /api/fleet/worker/session reseals cookie_enc whenever a worker hands its session back (claim.ts:790-838). The existing test covers only the 'session unchanged' order ('saves an edit over a fleet-resealed session ... while the session is unchanged').
  - Failure: A manager opens the Accounts page (snapshot holds account #12's storage state S1), a fleet worker on #12 saves its rotated session S2 (PUT /worker/session), then the manager edits #12's note and saves. The PUT writes S1 back over S2 and stamps cookie_at/cookie_by as the manager. The next claim of #12 restores S1, whose xs Facebook may already have invalidated, so the worker falls back to a password login (or SESSION_EXPIRED), i.e. a login the system was built to avoid.
  - Fix: Make the cookie (and token) write conditional: the client sends the cookie_at (or a hash of the cookie) it loaded; if the stored cookie changed since and the draft's cookie equals the loaded one, keep the stored cookie; if both changed, answer 409 so the manager reloads. Alternatively only write cookie_enc when the request carries an explicit cookieChanged flag.
  - Regression test: tests/facebook-pool.test.ts: load the snapshot, reseal the account's session through PUT /api/fleet/worker/session, then PUT the account with the earlier draft and a new note; assert cookie_enc still unseals to the worker's session and cookie_by is the worker id.
  - Verifier: repro/A4-verify/a4-02-editor-lost-update.test.ts (out: repro/A4-verify/a4-02.out.txt). Manager GET /api/facebook-pool returns cookie 'c_user=..; xs=S1-old'; worker PUT /api/fleet/worker/session stores xs=S2-rotated; manager PUT /api/facebook-pool/:no with the snapshot-seeded draft (note changed only) returns 200 and the stored cookie is back to 'xs=S1-old' with cookie_by='Alex Chen'. Code: AccountEditor.tsx seeds draft.cookie from the snapshot account; facebookPool.ts:484 writes cookie_enc = draft cookie unconditionally; :476 cookieUnchanged compares against the current stored cookie (S2), so it also restamps cookie_at/cookie_by. There is no updated_at or version check. (Reproduced. It needs a page left open across a worker reseal followed by a save, which is common for a manager editing notes. The cost is a stale session restored at the next claim, and so a likely password login. P2 is right.)

- [ ] **A4-03 / P2 / confirmed: POST /facebook-pool/:no/assign fires its Facebook-login side effects before any durable or locked state, and its final write has no status guard**
  - Location: `apps/backend/src/routes/facebookPool.ts:620-632, 656-696, 699-706`
  - Evidence: The eligibility checks (status, holder, 'already on worker') read the row with a plain SELECT outside any transaction or lock (:620-632). Then four external calls run: vault PUT /v1/accounts (:656), session seed (:680), restore-session (:689) or relogin (:694), each of which makes the worker sign in. Only afterwards does a transaction set status='fleet' with `WHERE no = ${no}` and no condition on the current status (:701-706). Nothing records an 'assigning' intent, so a failure after the relogin is queued (DB blip, process exit during deploy) leaves the worker logging in with an account the pool still shows as available/problem. This is the open architecture carryover 'Give external side effects durable lifecycle state' in this lane.
  - Failure: (a) Two managers assign #7 to rs-ne-1 and rs-ca-3 within a second: both pass the unlocked checks, both vault writes and relogins go out, two workers sign in to one account from two IPs (the location churn that gets accounts checkpointed); the last UPDATE wins the pool row. (b) A purchaser takes #7 between the check and the final UPDATE: the UPDATE silently flips it from 'taken' to 'fleet', the purchaser keeps using the login while the worker logs in too. (c) The backend restarts after the relogin was queued but before the UPDATE: the worker logs in, the pool still says 'available', and the next Take hands the same login to a purchaser.
  - Fix: Claim first, act second: in one transaction lock the row (FOR NO KEY UPDATE), re-check status/holder, and mark it with a durable 'assigning to <worker>' state (status or a pending column with requested_at); commit; then call the facade; then settle to 'fleet' (or roll back to the prior status on a refused call) with `WHERE no = $1 AND <pending marker matches>`. A sweep expires a stale pending marker the way wechat_market_reruns does.
  - Regression test: tests/facebook-pool.test.ts: stub the facade, start two /assign requests for the same account to different workers concurrently and assert exactly one reaches the facade relogin/restore; and take the account as a purchaser while a stubbed facade call is blocked, assert the assign returns 409 and the row stays 'taken'.
  - Verifier: repro/A4-verify/a4-03-assign-race.test.ts (out: repro/A4-verify/a4-03.out.txt), facade stubbed via fetch. (b) The purchaser POST /:no/take lands during the vault PUT and returns 200; assign returns 200 after PUT /v1/accounts/nyc-1 and POST /v1/workers/nyc-1/relogin; the row ends status=fleet, holder=nyc-1, so the purchaser's take is silently overwritten. (a) Concurrent assigns by alex (rs-ne-1) and sofia (rs-ca-3) both return 200 and both queue relogin (/v1/workers/rs-ne-1/relogin and /v1/workers/rs-ca-3/relogin); the row ends with holder rs-ca-3. Code: facebookPool.ts:620-632 plain SELECT (no lock) for the held/taken checks, :656-696 facade side effects, :699-706 UPDATE ... WHERE no = ${no} with no status/holder guard. (Scenarios (a) and (b) reproduced. Scenario (c), a crash between the relogin and the UPDATE, follows from the non-transactional ordering but was not reproduced. The route is manager-only and the window is a few facade round trips, but a double login from two IPs and a purchaser silently losing an account are both real. P2 stands.)

- [ ] **A4-04 / P3 / P3, not verified: Deleting a fleet proxy leaves parked slots holding its sealed URL; unparking them sends a worker out through the removed exit and outside the per-proxy cap**
  - Location: `apps/backend/src/fleet/proxies.ts:159-173; apps/backend/migrations/0213_fleet_proxies.sql:25; apps/backend/src/fleet/workers.ts:308-315; apps/backend/src/fleet/claim.ts:382`
  - Evidence: DELETE /fleet/proxies/:id only refuses while a non-parked slot uses the proxy (proxies.ts:166-171), so parked slots are allowed. fleet_slots.proxy_id is ON DELETE SET NULL (0213:25) but fleet_slots.proxy_url, the sealed copy, is left as is. /unpark clears the infinite lease without looking at the proxy (workers.ts:312-315), and claim unseals and hands slot.proxy_url (claim.ts:382, 418).   - Failure: A manager parks #31, deletes its proxy because the IP was flagged, later unparks #31 to put it back to work. The next claim hands the worker the deleted (flagged) exit; the worker restores or logs in to #31 from the burned IP, and the slot is invisible to the proxy list and the 2-per-exit limit.
  - Fix: On proxy delete, either refuse while any slot (parked included) references it, or null fleet_slots.proxy_url together with proxy_id; and have /unpark (and claim) refuse a slot with proxy_url NULL or proxy_id NULL, answering 'pick a proxy first'.
  - Regression test: tests/fleet-proxies.test.ts: add a slot, park it, delete its proxy, unpark it; assert unpark is refused (or the claim answers no proxy), never the deleted URL.

- [ ] **A4-05 / P3 / P3, not verified: Coordinator and tracker allowlists pass unvalidated path params, so a '..' id resolves to a parent upstream path**
  - Location: `apps/backend/src/routes/coordinator.ts:249-250, 500-506, 520-524; apps/backend/src/routes/tracker.ts:85-93, 113-116`
  - Evidence: These routes interpolate encodeURIComponent(param) without the WORKER_ID/ACCOUNT_ID checks the neighbouring routes apply (e.g. coordinator.ts:349, 356). encodeURIComponent leaves '.' unescaped, and fetch's WHATWG URL parser collapses dot segments: verified locally that '/v1/workers/' + encodeURIComponent('..') + '/relogin' fetches '/v1/relogin', and '/api/rules/..' fetches '/api/'. A request path with %2E%2E decodes to '..' in Hono's param.
  - Failure: A manager-session request POST /api/coordinator/challenges/%2E%2E/resolve reaches the facade as POST /v1/resolve, and /workers/%2E%2E/relogin as POST /v1/relogin; tracker DELETE /api/tracker/rules/%2E%2E becomes DELETE /api/. The allowlist's stated purpose (coordinator.ts:12-14, tracker.ts:10-14) is that the UI can only reach the listed upstream endpoints; this reaches unlisted ones one level up. Impact is bounded by what the upstreams expose there and requires a manager session.
  - Fix: Validate every forwarded id against its pattern before building the path (WORKER_ID for workers/:id, a uuid/int rule for challenges and rules, the subreddit name rule for subreddits), and reject '.'/'..' outright.
  - Regression test: tests/coordinator-routes.test.ts and tracker-routes.test.ts: request each param route with %2E%2E and assert 400 and that the upstream fetch mock was never called.
