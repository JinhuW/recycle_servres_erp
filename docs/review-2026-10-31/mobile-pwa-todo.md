## P2

- [ ] **A7-01 / P2 / confirmed: Mobile capture: a failed new-line autosave deletes the draft PO even when an earlier line already landed in it (photos and scan images deleted from R2)**
  - Location: `apps/frontend/src/MobileApp.tsx:627, :667-673 (with :170-175, :467-483); apps/backend/src/routes/orders/lifecycle.ts:62-110`
  - Evidence: onSaveLine computes `mintedHere = !editingId && !draftId` from the render-time snapshot (:627). ensureDraftId memoises one POST in draftIdPromise, so line A and a later line B saved before that POST resolved both get mintedHere=true and the same draft D. The write queue serialises them: A's PATCH lands and A is marked _confirmed with D's line id, and its photos are flushed to D. If B's PATCH then fails, its catch (:667) runs deleteOrder(D) without checking whether any line on the list is already confirmed (cancelCapture at :439 does check `!lines.some(l => l._confirmed)`, but this path doesn't). The backend DELETE removes a never-submitted draft with its lines and collects order_line_photos.storage_key and order_lines.scan_image_id for R2 deletion. A variant: A mints D and A's PATCH fails, so the fire-and-forget deleteOrder(D) races B's PATCH, which was queued with draftId=D; if B lands first, B's row and photos go with D.
  - Failure: On a slow cellular link a purchaser saves line A, which kicks off the draft POST, then adds line B and saves it while the POST is still pending. A syncs and its photos upload. B's PATCH hits a network error, so the app deletes PO D, including A's row, A's photos and A's label-scan image in R2. Because draftId was cleared, Submit then POSTs a new PO with both lines. A's line comes back, but its photos are gone and its scanImageId points at a deleted R2 object, so the thumbnail is broken. The user only saw a 'sync failed' toast for B.
  - Fix: Only delete a self-minted draft when nothing on it is confirmed: re-check via captureRef/setCapture at failure time (the same rule as cancelCapture), or track 'lines written to draft' per draft id. Better still, fold this into the shared capture state machine (carryover FE arch item), where a draft's lifetime is owned in one place.
  - Regression test: Render MobileApp (or extract onSaveLine), defer createDraftOrder, save A then B before it resolves, let A's addLines succeed and B's fail, and assert no DELETE /api/orders/D is sent and Submit PATCHes D rather than POSTing.
  - Verifier: Code trace: MobileApp.tsx:477 snapshots draftId from capture at Save; :627 `mintedHere = !editingId && !draftId` uses that snapshot inside the queued write; enqueueWrite (:168-174) serialises B after A, so by the time B runs A's POST resolved and A's addLines PATCH landed in D, and ensureDraftId (:467-483) returns the same memoised D. B's PATCH failure then hits :667-673 -> deleteOrder(D) (no check that another line confirmed into D) and clears draftId. Backend DELETE (orders/lifecycle.ts:62-160) collects order_lines.scan_image_id + order_line_photos.storage_key, deletes the order (lines cascade) and deleteAttachments() from R2. Uploaded photos are dropped from the client buffer on success (lib/linePhotos.ts flush: setPending keeps only failed), and submitOrder (:771-813) -> buildOrderSubmit (lib/orderSubmit.ts:70-78) takes the `create` path with toAddLine, which carries scanImageId (:65) but no photos and no carry plan (unlike the merge path's planCarry). Harness: docs/review-2026-10-31/repro/A7-verify/stale-minted-here.test.ts models the queue/ensureDraftId/mintedHere closure verbatim and calls the real buildOrderSubmit: `npx vitest run --root docs/review-2026-10-31/repro/A7-verify` -> 1 passed (asserts D deleted, Submit req.kind=create, line A scanImageId still 'orders/D/scanA.jpg'). (The stale-snapshot mintedHere makes a failed second save delete a draft that already holds a confirmed line; A's line is recreated on Submit but its photos are lost and its scan key points at a deleted R2 object. Not rendered end to end (no jsdom/testing-library in apps/frontend and pnpm install is forbidden), so the harness mirrors the component closure rather than mounting MobileApp. The window is narrow (B must be saved while A's draft POST is still pending, and B's PATCH must then fail), but the outcome is silent loss of user photos in a supported flow, so P2 stands.)

## P3

- [ ] **A7-02 / P3 / P3, not verified: Service worker precaches no .wasm, so the iPhone QR/DataMatrix serial scanner needs the network and fails silently without it**
  - Location: `apps/frontend/vite.config.ts:51; apps/frontend/src/lib/qr.ts:~85-95; apps/frontend/src/components/SnScanner.tsx:125-154`
  - Evidence: The injectManifest globPatterns are js,css,html,svg,png,webp,woff,woff2. The live sw.js on inventory.recycleservers.com lists 142 entries: every JS/CSS chunk referenced by the bundle (122/122, including assets/zxing_reader-*.js), but neither assets/zxing_reader-BxB2YfIY.wasm nor assets/mozjpeg_enc-DO-zoExo.wasm (both 200 application/wasm). qr.ts's own comment says 'the PWA must not depend on' a CDN fetch, yet the wasm still comes from the network. iOS has no BarcodeDetector, so it always takes the zxing path. In SnScanner the decode loop is an async IIFE whose `await createFrameDecoder()` has no catch.
  - Failure: An iPhone purchaser in a warehouse dead spot opens the serial scanner. The wasm fetch fails, createFrameDecoder rejects as an unhandled rejection, and the scan line keeps animating with no error. Nothing ever decodes, and there's no hint to switch to AI or typing. MozJPEG falls back to the canvas encoder, so only the QR path breaks.
  - Fix: Add 'wasm' to globPatterns, and raise maximumFileSizeToCacheInBytes if the reader exceeds 2 MiB. Catch the createFrameDecoder rejection in SnScanner and set camError or a 'decoder unavailable, use AI/typing' note.
  - Regression test: A build-output test asserting every assets/*.wasm is in the injected precache manifest. A unit test where a rejecting createFrameDecoder makes SnScanner surface an error state.

- [ ] **A7-03 / P3 / P3, not verified: Camera shutter uploads an 8-byte fake PNG when the live stream isn't up (permission denied or still starting)**
  - Location: `apps/frontend/src/pages/Camera.tsx:112-127, :168-178, :317-321`
  - Evidence: captureFrame returns a synthetic 8-byte PNG when videoWidth is 0, commented 'The stub OCR ignores the bytes anyway', and the shutter is enabled whenever phase==='framing'. In production /api/scan/label (apps/backend/src/routes/scan.ts:84-120) accepts image/png, uploads it to R2 and sends it to the OpenRouter OCR model.
  - Failure: An iOS PWA user who denied the camera, or taps before the stream attaches, presses the shutter. A junk object is written to R2 label-scans, a billed LLM call runs and counts against the 20/min scan limit, and the user gets an unreadable or garbage result instead of a 'camera unavailable — upload a photo' prompt.
  - Fix: Without a live frame, disable the shutter or route it to the file picker. Keep the placeholder only behind import.meta.env.DEV.
  - Regression test: Camera with getUserMedia rejected: pressing the shutter makes no /api/scan/label request and opens the picker or shows cameraUnavailable.

- [ ] **A7-04 / P3 / P3, not verified: Mobile review screen holds unsynced lines with no unsaved-change guard, so the PWA update toast or a layout switch drops them without asking**
  - Location: `apps/frontend/src/MobileApp.tsx:912-927; apps/frontend/src/components/PwaUpdateToast.tsx:55-65; apps/frontend/src/lib/unsavedGuard.tsx:60-64`
  - Evidence: Only SubmitForm calls useUnsavedGuard. Capture state lives in MobileApp's useState, and in the review phase lines can be unconfirmed (sync failed or blocked), _dirty, or still in flight (pendingWrites>0). No guard is registered for that, so confirmDiscard() resolves true and the update toast reloads straight away. iOS shows no beforeunload, as PwaUpdateToast's own comment notes.
  - Failure: A line's autosave fails ('sync failed', kept locally for Submit). The user then taps 'Update' on the new-version toast. The page reloads and the unsynced line is gone without any prompt.
  - Fix: Register useUnsavedGuard(capture.phase==='review' && (pendingWrites>0 || lines.some(l => !l._confirmed || l._dirty)), () => true) in MobileApp, or in OrderReview with the same inputs.
  - Regression test: Review with an unconfirmed line: confirmDiscard() resolves only after the discard dialog is answered.

- [ ] **A7-05 / P3 / P3, not verified: CSP has been report-only for 4 weeks with no reporting endpoint, and the shared-photo handoff already violates it**
  - Location: `apps/frontend/public/_headers:13-14, :28; apps/frontend/src/pages/Camera.tsx:134`
  - Evidence: The policy has been Content-Security-Policy-Report-Only since b9ad1719 (2026-10-02, v1.194.2) and has no report-uri or report-to, so violations show only in each user's console and the 'until a release shows no violations' exit can't be observed. Camera.tsx:134 calls fetch(sharedDataUrl) on a data: URL from sharedFile.ts, and connect-src lists no data:, so the Web Share flow is an existing violation that would break the moment the policy is enforced. The live header matches the repo, and csp-rev=1 is consistent: the CSP is unchanged since csp-rev was introduced, so there's no missing bump.
  - Failure: Someone flips the header to enforcing because 'no violations were seen' (there was no channel to see them). Sharing a photo into the installed app then fails with cameraUnavailable on every share.
  - Fix: Add a report-to/report-uri endpoint, or a small backend collector, before deciding on enforcement. Convert the data URL with a non-fetch decode (atob → Blob), or add data: to connect-src. Bump csp-rev with any header change.
  - Regression test: A test that parses _headers and asserts connect-src covers every fetch() scheme used in src. A share-target e2e run under an enforced policy.
