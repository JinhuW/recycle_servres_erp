# Infrastructure and integrations TODO — 2026-10-13

Reviewed snapshot: `55b5a15a`, version `1.247.2`. Priorities describe this application's impact: P1 urgent, P2 normal corrective work, P3 maintainability. Findings are open; this review does not implement fixes.

- [ ] **INF-01 / P2 — Gate frontend deployment on checks for the same commit, including Worker changes.** `.github/workflows/deploy-frontend.yml:48-59` installs and invokes a deployment; it has no dependency on `backend-tests` or `version-check`. A failed push check does not stop this separate workflow from publishing. In addition, `.github/workflows/backend-tests.yml` does not trigger for `deploy/cloudflare/**`, although that Worker controls API forwarding and client identity. Branch protection configuration was not inspected, so this finding concerns the workflows' own behavior, not an assertion about current protection rules. Add same-commit test/typecheck/build prerequisites and Worker behavior tests for forwarding, headers, methods, and asset misses. Verify that a deliberately failing check prevents deployment before credentials are used.

- [ ] **INF-02 / P2 — Include every supported application origin in the R2 read CORS policy.** `infra/terraform/modules/cloudflare/variables.tf:39-43` allows only `https://inventory.recycleservers.com`; `infra/terraform/environments/prod/main.tf:24-31` inherits that default. `deploy/cloudflare/wrangler.toml` also declares `inventory-prod` and `inventory-dev`. `apps/frontend/src/lib/linePhotos.ts:283-297` fetches stored photos when carrying them into replacement lines, so these declared alternate origins cannot complete that operation under the committed Terraform policy. Set an explicit origin list in the environment composition and test photo carry from each origin. See [Cloudflare R2 CORS documentation](https://developers.cloudflare.com/r2/buckets/cors/). The live bucket policy was not queried; this is a verified config mismatch, not a claim about live manual overrides.

- [ ] **INF-03 / P2 — Claim Shippo subscriptions atomically across create-time registration, sweeps, and deployment overlap.** `apps/backend/src/routes/packages.ts:220-227` detaches registration after INSERT; `apps/backend/src/shipping/track.ts:130-140,161-178` independently reads rows with a NULL registration stamp and registers them before updating the stamp. A create request racing a sweep, or two backend processes during a rolling deploy, can both register the same number. The loop's process-local `running` flag covers only its own ticks. Introduce a database-backed claim/lease and an explicit policy for uncertain provider outcomes, because retrying a successfully delivered POST whose DB stamp failed also duplicates a subscription. Test two concurrent callers with a blocked fake provider and assert one external registration. Current [Shippo tracking documentation](https://docs.goshippo.com/tracking/tracking) confirms duplicate registrations can produce multiple notifications. Choose retry semantics that account for uncertain outcomes.

- [ ] **INF-04 / P2 — Make the destructive sync target identity mandatory and independent of hostname spelling.** `deploy/railway-sync/sync.sh:25-53` refuses equal URL strings or host strings, but its target pin is optional. The same Postgres database reached through its public proxy and private/internal hostname passes both comparisons; the subsequent `DROP SCHEMA ... CASCADE` would then restore and scrub that database. Require an explicit expected dev identity/pin and verify it before restore (ideally a dev-only role and database identity marker). This is a guard weakness under misconfiguration, not evidence that production is currently targeted. Test aliased source/target URLs using stub commands, ensuring refusal before `pg_dump`/`psql` performs a mutation.

- [ ] **INF-05 / P3 — Encode uptime alerts as JSON and check application-level delivery.** `deploy/railway-uptime/check.sh:40-47` interpolates `$msg` directly into JSON and calls curl without HTTP failure handling. A configured URL containing JSON-significant characters makes an invalid payload; HTTP errors, or a Lark API error inside HTTP 200, appear as a successful alert POST. The cron still exits 1 for the outage, but staff can miss the notification. Generate JSON with a serializer and validate the response code/body. Test a URL with a quote, HTTP 500, and provider rejection in an HTTP 200 body using local fake endpoints.

- [ ] **INT-01 / P2 — Lock and revalidate automatic reconciliation decisions before persisting them.** `apps/backend/src/banktx/sync.ts:470-558,591-600,690-714` selects pairing/linking candidates before later unconditional UPDATEs. Process-local sync single-flight excludes other sync calls in that process, but does not serialize a manager's pair/unpair/ignore/link action or another backend process. A manager's unpair or reassignment committed after candidate selection can be overwritten; a stale link can replace their decision. Use row locks in a consistent order and post-lock precondition reads or conditional UPDATEs, including both pair legs. Coordinate with the manual reconciliation fix in the backend domain TODO. Add tests that pause after automatic selection, perform the manager action, then release the sync and assert the manager's verdict survives.

- [ ] **INT-02 / P3 — Enforce the PO-review image byte limit while reading the stream.** `apps/backend/src/ai/poReview.ts:26-30` reads the entire response with `arrayBuffer()` before testing the 15 MiB limit. That limit cannot bound peak allocation, and concurrent label rereads multiply the allocation. Reject oversized Content-Length where available and stop/cancel the body stream once the limit is reached, with the existing timeout retained. Test a chunked response exceeding the cap and assert reading stops at the limit. Current uploads normally bound object size; this is a resource-boundary defect rather than an asserted unauthenticated attack on arbitrary URLs.

- [ ] **INT-03 / P3 — Validate AI JSON shape and count only expected fields toward confidence.** `apps/backend/src/ai/prompts.ts:104-119` casts every parsed JSON value to a record without checking shape; `apps/backend/src/ai/openrouter.ts:245-254` counts all nonempty strings, including unknown keys, toward the coverage confidence floor. A mocked current transport reply with `_confidence:0` and eight unknown strings returned RAM confidence 0.8 despite containing no expected RAM field. `parseModelJson('42')` also returns a number and `parseModelJson('[]')` returns an array. Require a plain object, validate each consumer's schema, and derive coverage from recognized usable fields after normalization. Preserve legitimate partial reads. Regression: unknown keys cannot inflate confidence; arrays/scalars trigger the retry/refusal path; ordinary partial field reads retain their confidence contract. Reproduction: [integration-probes.mjs](integration-probes.mjs), executed successfully with mocked fetch and no external model call.

## Structure and recovery follow-ups

- [ ] **INF-06 / P2 — Add an automated isolated restore drill for offsite backups.** `backup/backup.sh:66-88` verifies that `pg_restore --list` can read a TOC and that key tables have data entries; neither proves every archived data block can restore or that the restored schema is usable. `backup/README.md` documents manual recovery, but no restore drill is implemented in the repository's workflows. Periodically download a selected R2 backup, restore into a disposable Postgres 18 database, check business invariants and migration compatibility, and retain the result. Keep production and dev untouched.

- [ ] **INF-07 / P3 — Typecheck and enable persistent observability for the Worker.** `deploy/cloudflare/worker.js` is plain JS outside the workspace TypeScript checks, and `deploy/cloudflare/wrangler.toml` does not configure observability. Add generated binding types or checked JS, a local behavior test target, and explicit log/tracing settings with a deliberate sampling policy. This is a maintainability/diagnostic improvement, not a known runtime failure. Reference: [Cloudflare Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/).
