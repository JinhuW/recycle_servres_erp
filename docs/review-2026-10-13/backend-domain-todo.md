# Backend domain review TODOs

Reviewed the current worktree on 2026-10-13. P1 = high priority correctness/integrity issue; P2 = actionable defect; P3 = maintainability improvement. Items are deliberately unchecked: this review does not change application behavior. Runtime evidence below uses an isolated PostgreSQL 18 database with the repository's migrations, seed, Hono application, and existing test helpers. The reproduction assertions demonstrate the defective behavior, rather than asserting a fix.

- [ ] **BD-01 — P1: Serialize manual bank pairing before reading either leg.** `apps/backend/src/routes/bankTx.ts:530-572` reads both groups and checks `pair_id` before opening its transaction, then unconditionally overwrites both legs. Concurrent requests pairing Mercury A with PayPal B and PayPal C both return 200, leaving B or C alone under its old `pair_id`. The payment feed and PO paid totals suppress paired Mercury legs, so malformed groups can hide or miscount money. **Verified:** hold A's row lock, start both endpoints, wait until both UPDATEs are blocked, release: both succeed and group sizes are `[1, 2]`. **Fix:** acquire all relevant leg/group locks in stable order inside one transaction, re-read group membership and validate under those locks; coordinate with automatic pairing and unpairing. **Regression:** one request succeeds and the rival gets a conflict; every surviving pair has exactly the intended two sources with matching group state.

- [ ] **BD-02 — P1: Read sell commitments after transfer reopen obtains its inventory locks.** `apps/backend/src/routes/inventory.ts:1978-1996` computes `committedQtySql` in the same `SELECT ... FOR UPDATE` that may wait on promotion. PostgreSQL's statement snapshot remains older than a rival sale that commits while the SELECT waits; promotion locks the inventory row without changing its tuple. Reopen therefore sees `sell_count = 0` and moves stock to In Transit despite a committed Shipped order. **Verified:** a transaction locks the lot, reopen blocks on its SELECT, the transaction promotes its SO to Shipped and commits; reopen returns 200 and the source lot is In Transit while the SO is Shipped. **Fix:** lock the inventory rows first, then query `committedClaimsByLine` in a separate statement, as `validateSellLines` already does. Sweep other correlated precondition queries embedded in locking SELECTs. **Regression:** the same interleaving returns 409 and preserves the received stock status.

- [ ] **BD-03 — P2: Recheck bank reconciliation verdicts inside the mutation transaction.** `apps/backend/src/routes/bankTx.ts:425-455,648-656` checks link/ignore eligibility on unlocked snapshots; `apps/backend/src/routes/internalTx.ts:177-211` similarly checks membership before an unguarded UPDATE. **Verified:** block a free payment's row, start link and ignore, wait for both UPDATEs, then release: both return 200 and the final payment has both `order_id` and `ignored = true`. `apps/backend/src/banktx/match.ts:201` then excludes this allegedly linked payment from the PO paid total. The same pattern allows two internal records to pass the 'already belongs elsewhere' check and the later writer silently steals membership. **Fix:** share a locked group mutation service, expand and lock the current group under the same transaction, then validate and mutate. Add suitable row CHECKs for incompatible state as a backstop. **Regression:** concurrent link/ignore and concurrent record filing yield one accepted verdict and one explicit conflict, never a hidden paid amount or stolen membership.

- [ ] **BD-04 — P2: Include inventory-free sale lines in financial reporting.** `apps/backend/src/routes/dashboard.ts:115-118,146-149,164-169,187-190,291-294` and `apps/backend/src/services/contributions.ts:79-83` INNER JOIN each sale to `order_lines`. Manual sell lines are supported (`createSellOrderDraft` stores `inventory_id = NULL`) but disappear from revenue, sale count, chart, and customer/category contributions. Completed-sale source lines can also later be deleted with FK SET NULL (`migrations/0127_sell_order_lines_inventory_set_null.sql`, `routes/orders/patch.ts:570-605`), so existing financial history can vanish for the same reason. **Verified:** create a valid manual-only sell order for two $50 rails, complete its header in the fixture, and request the actual dashboard: revenue and completed-order count are both 0. **Fix:** aggregate revenue and SO counts from sale snapshots independently of inventory linkage; represent unknown/manual cost explicitly and retain historical cost/attribution snapshots where financial readers require them. **Regression:** manual-only and mixed orders retain all $100 revenue; deleting an allowed source reference does not erase historical sale revenue.

- [ ] **BD-05 — P2: Validate purchaser ownership against the locked PO row.** `apps/backend/src/routes/orders/patch.ts:113-115,309-343` checks owner before the transaction but does not repeat it after locking `orderBefore`. `apps/backend/src/routes/inventory.ts:1289-1299,1327-1349` has the same stale check and explicitly assumes the parent owner cannot change, whereas `apps/backend/src/services/orderHandoff.ts:325-335` does change it. **Verified:** lock a purchaser's Draft, let their PATCH pass the ownership probe and block, reassign `user_id` to another purchaser before releasing the lock: the old owner gets 200 and writes notes onto the new owner's PO. **Fix:** repeat the role/owner gate after locking the authoritative PO in both routes and `routes/orders/evidence.ts:81-103` (status-note writes also use an unlocked owner/lifecycle snapshot); use the locked owner for all dependent checks. **Regression:** that interleaving returns 403 with no writes, audit events, or lifecycle reversion.

- [ ] **BD-06 — P2: Unify PO/SO header lock order for archive and Done.** PO archive locks `orders` first (`apps/backend/src/routes/orders/lifecycle.ts:178-181`), then locks its sell orders (`apps/backend/src/services/orderAdvance.ts:374-380`). Sell-order Done locks `sell_orders` first (`apps/backend/src/routes/sellOrders.ts:1400-1402`) and then owning POs (`:1447-1453`). **Verified:** hold the PO archive lock, start the real Done endpoint and wait until it waits for that PO, then run `archiveOrderLinesTx`: PostgreSQL raises deadlock `40P01` for one operation. `stock-lock-order.test.ts` covers Done versus PO PATCH but misses archive's additional SO lock. **Fix:** define one lock protocol covering both header kinds and source lines, discover/revalidate relevant IDs safely, and apply it to archive, Done, and line rewrites. Retry deadlock victims only as a secondary resilience measure. **Regression:** barrier-controlled archive versus Done always settles without a 500 and preserves inventory, sign-off, and sale-line integrity.

- [ ] **BD-07 — P2: Preserve all duplicate inventory-backed lines in sell-order audit diffs.** `apps/backend/src/services/sellOrderLineMatch.ts:35-46` puts each inventory ID into a single-entry Map, overwriting earlier occurrences. The API and packing module explicitly support naming one lot multiple times, so the helper's one-line-per-lot assumption no longer holds. **Verified:** before quantities `[1, 2]`, after `[10, 2]`, same lot for both entries: `diffSellOrderLines` returns zero added, removed, or edited entries even though the saved quantity/cash total changed. **Fix:** match inventory-backed occurrences as a multiset using stable semantic identity/occurrence rules, or preserve row identity across rewrites; cover duplicate removal as well as edits. **Regression:** the first occurrence's edit/removal appears in SO history and workspace activity exactly once.

- [ ] **BD-08 — P2: Apply field validation consistently to catalog and customer creation.** `apps/backend/src/routes/categories.ts:45-70` does not invoke the validator used at `:90`; `apps/backend/src/routes/customers.ts:81-95` likewise omits the validator used at `:109`. A negative default margin and an invalid contact email enter the database via POST although the same fields are rejected via PATCH. **Verified:** POST category `defaultMargin: -1` and customer `contactEmail: 'not-an-email'` both return 201; PATCH with those same values returns 400. **Fix:** reuse the shared present-field validators on creation and require nonblank appropriately typed identifiers/names before SQL; add matching database constraints for numeric invariants. **Regression:** POST and PATCH enforce the same supported domain and consistently answer 400 for malformed values.

- [ ] **BD-09 — P2: Lock an item type before reading the old name used by its rename sweep.** `apps/backend/src/routes/itemTypes.ts:79-105` reads `existing.name` without `FOR UPDATE`, updates the catalog row, and sweeps lines matching the previously read name. Two concurrent renames from A to B and A to C both read A; after the first sweep A→B, the second catalog update reaches C but its A→C sweep matches no lines. **Verified:** block the item-type row, start both rename endpoints, wait for both UPDATEs and release: both return 200; the final catalog name and an originally matching PO line's `item_type` disagree. **Fix:** lock/read the item-type row first and serialize rename with line writers; consider storing an item-type FK instead of mutable display-name references. **Regression:** parallel renames leave every affected line referring to the final catalog name, without splitting usage counts.

- [ ] **BD-10 — P2: Make the partial-sale integrity test independent of randomized seed quantities.** `apps/backend/tests/tier1-data-integrity.test.ts:30-44` asks for a free lot with at least two units, sells two, and always expects stored qty to fall by two. On an exactly-two-unit lot, the documented full-sell rule retains qty and changes status to Sold (`apps/backend/src/routes/sellOrders.ts:1585-1592`). **Observed:** the root full-suite run failed this assertion; an isolated targeted rerun passed because a different random lot was selected. **Fix:** create/set a deterministic lot with more than two units for the partial-sale test and add a separate full-sell assertion checking Sold plus retained purchased quantity. **Regression:** the test is stable across seeds and covers both intentional branches. This finding does not claim the intended full-sale retention is a production bug.

- [ ] **BD-11 — P3: Move packing persistence helpers out of the HTTP route module.** `apps/backend/src/services/orderAdvance.ts:18` imports `prunePackRows` from `routes/sellOrderPack.ts`, while that route imports services; `routes/sellOrders.ts` imports the same route helper. This makes lifecycle/domain code depend on HTTP registration and produces an avoidable route/service import cycle. **Fix:** extract keyed-line identity, packing reads/writes, and pruning into a domain service used by both routers and lifecycle code; keep Hono handlers as authorization/validation/response adapters. **Validation:** dependency direction is route→service→DB/shared, and existing packing/archive tests remain green. This is a structural improvement, not a reproduced runtime failure.
