## Verified issues

- [x] **SEC-01 · P1 · Reject authorization codes issued before a password reset.** `apps/backend/src/oauth/server.ts:539–579`; `apps/backend/src/services/members.ts:123–147`; `apps/backend/src/routes/me.ts:193–213`. A client can obtain a code, wait for a manager to reset the user's password, and redeem the old code within its ten-minute lifetime. Reset revokes refresh tokens but leaves authorization codes usable. Redemption does not read the live user or a credential version; its newly signed `iat` passes the bearer's cutoff and it creates a new refresh family after the reset. The same path preserves consented manager scopes when redemption happens after demotion. **Evidence:** an isolated integration repro reset the password, observed 401 for the old cookie, then redeemed the old code to a 200 token response and a 200 authenticated MCP response; a second repro retained `market:write` after demotion. **Remediation:** bind pending consent/codes to a credential/session version, invalidate them atomically during reset/offboarding, and recheck active status, credential version and live role inside code redemption. Coordinate redemption and reset on the same user lock/version so concurrent redemption cannot recreate a revoked grant. **Regression:** consent → reset → redeem must return `invalid_grant`; consent → demote → redeem must reject or narrow scopes; include concurrent reset/redemption and inactive/reactivated-user cases.

- [x] **SEC-02 · P2 · Make access cookies observe session-family revocation.** `apps/backend/src/auth.ts:118–133`; `apps/backend/src/routes/auth.ts:185–196`; `apps/backend/src/vncBridge.ts:221–230`. Auth checks the user's active flag and password cutoff but never checks the JWT's `fid` against the family. Logout and stolen refresh-token reuse revoke only refresh rows. A copied access cookie therefore continues to authorize requests for up to its remaining one-hour lifetime after logout or reuse detection. VNC's periodic recheck also continues admitting that cookie after logout, contrary to its documented behavior. **Evidence:** integration repro logged out with both cookies, then fetched `/api/me` using the saved access cookie and received 200. **Remediation:** track family/session liveness and consult it during auth, including VNC rechecks; ensure normal rotation does not mark the session itself revoked. **Regression:** saved cookie fails after logout/reuse revocation, unaffected families still work, and an open viewer closes after logout.

- [x] **SEC-03 · P2 · Replace second-resolution password revocation with a credential version.** `apps/backend/src/auth.ts:58–61,123–124`; `apps/backend/src/services/members.ts:122–139`; `apps/backend/src/routes/me.ts:196–198`; `apps/backend/src/oauth/guard.ts:36–40`. Tokens minted immediately before a password change in the same second compare equal to `tokens_valid_after` and remain accepted. The cutoff is rounded down and the test suite even asserts equality is permitted. This contradicts the intended revocation of all previously issued access tokens and can last for the full remaining token lifetime. **Evidence:** deterministic integration repro fixed the app clock, logged in, reset the password and still received 200 on `/api/me` with the old token. **Remediation:** put a monotonically incremented credential version in both token types and compare against the live user; issue replacement tokens using the new version. **Regression:** token minted before change in the exact same second fails; replacement token succeeds without waiting for the clock to advance.

- [x] **SEC-04 · P1 · Serialize the last-active-manager invariant with member writes.** `apps/backend/src/routes/members.ts:149–156,168–173`; `apps/backend/src/services/members.ts:164–169`. The manager count is read before the separate update/deactivation transaction. With two managers, concurrent self-demotions both see the other active manager and both succeed, leaving zero managers and no authorized way to recover through the application. **Evidence:** integration repro locked both user rows to synchronize two self-demotion PATCHes; both returned 200 and the final active-manager count was zero. **Remediation:** use a common transaction/advisory lock for all operations changing active-manager membership, count under that lock, then write and revoke tokens in that transaction. Locking only each target row does not protect the cross-row invariant. **Regression:** simultaneous demotions/deactivations leave at least one active manager and one request fails cleanly; mixed PATCH/DELETE paths share the protection.

- [x] **SEC-05 · P2 · Refuse successful production attachment uploads when R2 is absent or partially configured.** `apps/backend/src/r2.ts:49–55,94–102,167–170`; `apps/backend/src/env.ts:23–67`. Production startup validates several provider secrets but accepts a missing R2 configuration. Upload returns a `stub-` key and a data URL containing only a filename, without the original file bytes. Evidence routes can then persist a successful attachment record while the user's receipt/photo is permanently lost. Copying a real object under incomplete configuration similarly creates a stub reference. **Evidence:** repro built a valid production Env without R2 and uploaded a PDF; the provider was `stub` and no evidence bytes were stored. **Remediation:** enforce explicit storage modes; permit stubs only in development/tests, fail production upload/copy closed with an actionable unavailable response, and expose attachment-provider readiness. **Regression:** omitted or partially configured production credentials never report successful persistence; development stub behavior is tested explicitly.

- [x] **SEC-06 · P2 · Bound both directions and the pre-connect queue in the VNC bridge.** `apps/backend/src/vncBridge.ts:141–152,183–193,250`. The browser-bound stream has a 16 MiB buffered check, but browser messages arriving before ticket/upstream setup append to an unbounded array; after setup, every message calls `upstreamSocket.send` without checking its buffered amount. A broken or modified authenticated viewer, or a slow facade, can consume backend memory until the shared ERP process dies. A cap on eight sockets does not cap queued bytes per socket. **Evidence:** source tracing shows no pending-byte counter, no upstream buffered check and no explicit WebSocket message-size cap. **Remediation:** enforce per-frame size, total pending bytes and upstream buffered bytes; pause/resume where supported or close a slow/abusive peer, clearing queued bytes on failure. **Regression:** slow ticket response plus a client burst remains below a fixed byte ceiling; blocked upstream writes trigger a bounded close; normal screens/input still relay.

- [x] **SEC-07 · P2 · Reserve public-form daily quotas atomically before image work.** `apps/backend/src/routes/publicForms.ts:63–81,348–349,399–420,441–446`. Daily submission/byte/IP counts are checked outside the insertion transaction, before potentially slow image processing and uploads. Parallel requests all see the same remaining room and can overshoot the promised database-backed budget; across replicas the process-local minute limit also multiplies. The budget counts only successful stored rows, so expensive uploads from failed requests never consume a reservation. **Evidence:** every request reads aggregate counts, performs external work, then inserts without locking/rechecking the budget. **Remediation:** persist an atomic per-day reservation for submissions, sender share and estimated bytes before processing; settle stored bytes and release failed reservations with bounded expiry. **Regression:** concurrent requests with one slot/byte share left admit only the permitted quota across replicas; failed uploads do not leak reservations.

- [x] **SEC-08 · P2 · Make anonymous OAuth registration quotas atomic.** `apps/backend/src/oauth/server.ts:122–145,213–222`. DCR counts registered clients before validation and bcrypt/create, then inserts without a shared reservation or lock. Simultaneous registrations can all pass the per-IP/hour/global/unused checks, defeating limits specifically described as a security boundary and storing excess clients. **Evidence:** the count and `createOAuthClient` are independent operations with no transaction or reservation connecting them. **Remediation:** claim durable slots under a shared database lock/counter before secret hashing and client creation; roll back/release failed reservations and bound abandoned records. **Regression:** concurrent public and confidential registrations at the last available slot produce one success and the expected 429s; multiple replicas obey the same counts.

- [x] **SEC-09 · P2 · Serialize stale-submission purge with triage and conversion.** `apps/backend/src/lib/webSubmissionPurge.ts:33–55`; `apps/backend/src/routes/webSubmissions.ts:184–197,327–338,395–400`. Purge selects old archived/spam submissions, deletes their objects, then deletes rows using only the previously collected IDs. While object deletion is in flight a manager can reopen or convert the submission. Purge still deletes the now-active/converted submission and its mail history; reopening can also retain photo URLs whose objects were already removed. The conversion row lock does not interact with the unprotected purge. **Evidence:** the final DELETE has no status, `updated_at`, `order_id` predicate or held lock, and external deletion occurs after an unlocked snapshot. **Remediation:** claim eligible rows with a purge state/version under a lock and make triage/conversion respect that claim; finalize only the claimed version after storage deletion. A final SQL predicate alone cannot undo already-deleted photos. **Regression:** delay object deletion while reopening/converting the row; no converted/reopened record or referenced photo is lost.

- [x] **SEC-10 · P2 · Reserve password-change failures before bcrypt.** `apps/backend/src/routes/me.ts:153–168,176–183`. Unlike login, the password-change route reads the failure count first and records failures after comparison. A holder of a valid access cookie can submit a concurrent burst of current-password guesses; every request passes the same initial count and enters bcrypt regardless of the five-attempt budget. The semaphore bounds work at once but does not enforce the security attempt limit. **Evidence:** no pending attempt is reserved or counted before verification; login's reservation pattern at `routes/auth.ts:75–98` provides an existing contrast. **Remediation:** share the durable attempt-reservation helper with login, clean up refused/failed infrastructure attempts, and consider a dedicated per-session/account budget that cannot be cleared by unrelated login successes. **Regression:** a concurrent burst yields at most the configured number of allowed guesses and no unexpected bcrypt work after the budget is exhausted.

- [x] **SEC-11 · P3 · Reject inherited keys in the preference schema lookup.** `apps/backend/src/preferences.ts:53–66`. `SCHEMA[key]` reads `Object.prototype`: `toString` and `constructor` are accepted as callable validators and persist unknown preferences; a JSON `__proto__` value can reach a non-callable inherited object and throw 500. **Evidence:** direct repro showed `{toString:'unknown'}` and `{constructor:'unknown'}` return `ok:true`. **Remediation:** require `Object.hasOwn(SCHEMA,key)` or use a null-prototype/Map schema; construct cleaned output safely. **Regression:** every inherited name (`constructor`, `toString`, `__proto__`, `hasOwnProperty`) returns the normal 400 unknown-key response with no persistence.

- [x] **SEC-12 · P3 · Merge preference patches against the current row atomically.** `apps/backend/src/routes/me.ts:90–110`. PATCH starts with the preferences loaded earlier by auth and writes the entire JSON document back. Two tabs saving different settings concurrently can both start from the same snapshot; whichever finishes last erases the other change. An unrelated patch can also overwrite a concurrent language-column change with `u.language`. **Evidence:** there is no row lock/version check or JSONB merge in the UPDATE. **Remediation:** apply allowlisted sets/removals to live JSONB in one UPDATE or re-read under a row lock; only update the language column when that key is supplied. **Regression:** simultaneous independent key patches retain both values; a non-language preference save does not revert a concurrent language change.

- [x] **SEC-13 · P3 · Use unique error-log rotation names.** `apps/backend/src/lib/error-log.ts:158–161,183–195`. Rotation filenames contain only seconds. If two rotations occur in one second, the second `fs.rename` replaces the first rotated file, silently destroying its records despite the configured ten-file retention. **Evidence:** deterministic filesystem repro performed three appends with a one-byte test threshold under a fixed clock; record 0 disappeared while record 1 remained in the overwritten rotated path. The smaller threshold exercises the same production rotation branch. **Remediation:** add a unique suffix/counter and ensure creation cannot overwrite an existing archive; adapt pruning to the new filename shape. **Regression:** several same-second rotations retain every record and honor maximum-file retention.

- [x] **SEC-14 · P2 · Bound anonymous login credential fields before durable writes.** `apps/backend/src/routes/auth.ts:24–29,47–77`. The login route checks only nonempty string types. A body below the general 1 MiB cap can use a near-megabyte arbitrary email, which is lowercased, queried and persisted in `login_attempts`; repeated distinct emails bypass account counters and turn an anonymous authentication surface into large durable database/index writes. Password input is also unbounded before bcrypt. **Evidence:** no email-format/length or password-length validation exists before the reservation INSERT. **Remediation:** bound email and password to supported sizes before normalization, count/reservation queries or bcrypt; reject malformed email strings with the ordinary input response. Preserve support for existing valid credentials within the actual password storage limits. **Regression:** oversized/malformed inputs return 400 without a login-attempt insert or bcrypt execution; valid boundary-size credentials still work.

- [x] **SEC-15 · P2 · Clean up sell-order receipt objects when their database transaction fails.** `apps/backend/src/routes/sellOrders.ts:1138–1164`. Upload commits a public R2 object before inserting the attachment and audit event. If either SQL operation fails, including a concurrent sell-order deletion after the initial existence check, the request fails while the receipt stays public with no database record or normal delete action. The comment delegates orphan handling to R2, but `r2.ts` supplies no sweep or compensation. Purchase-order evidence already compensates for this failure. **Evidence:** source tracing confirms the SQL transaction has no catch invoking `deleteAttachment`; no object inventory/sweeper was found. No live bucket was used. **Remediation:** wrap the transaction in compensating deletion and durably retry failed cleanup; alternatively track pending storage objects and finalize them only after the SQL commit. **Regression:** inject attachment-insert and audit-write failures after a successful stubbed upload and assert deletion is attempted; test cleanup failure retry and concurrent order deletion.

## Architecture assessment

The Hono entrypoint centralizes request context, proxy authentication, CORS, CSRF, body limits and route mounts. Member business logic is separated from HTTP routes, query interpolation uses postgres.js bindings, public inputs have several explicit bounds, and OAuth/MCP tools have separate cookie/bearer guards and scopes. Those are useful foundations. The main structural weakness is that important invariants remain split across route handlers and independent SQL/external operations: session revocation, credential validity, cross-member manager counts, quotas and object deletion need a shared transactional/state model. Existing comments sometimes promise stronger semantics than those operations enforce. No broad rewrite is needed to address the listed defects; central helpers for session/credential versions, durable reservations and storage-operation state would reduce repeated mistakes.
